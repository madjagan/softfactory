## 1. The shape of the factory

One repo runs as a closed loop with four actors and one ledger:

| Actor | Role |
|---|---|
| **Product owner** (human) | Adds requirements, decides money/statutory questions, asks for sweeps, commits |
| **Claude Code + skills** | Runs gated pipelines: spec → red test → build → prove → log |
| **Human evaluators** (non-developers) | Run the structured test plan, then explore; file findings with screenshots |
| **Subagents** | `docs-agent` (documentation authority), `evaluator-assistant` (sits beside the tester) |

The **ledger is the `docs/` folder plus the issue tracker**. The governing rule, repeated in every skill: *work that is not in the ledger did not happen.*

```
 requirement (PRD §3.x, dated)
      │  /create-feature
      ▼
 RED acceptance test ──► plan entry (dated, risks) ──► build ──► GREEN + full suite + real flow
      │                                                                     │
      │                                                                     ▼
      │                                                    issues_log.md entry · PRD/plan flipped ✅
      │                                                                     │
      ▼                                                                     ▼
 FEATURE_LIST.md (traceability, maturity ●/◐/◐!) ──hook──► docs-agent ──► user-guide/*.md (derived)
      │
      ▼
 TEST_PLAN_HUMAN.md (90 rows) + TESTING_COMPANION.md (charters) ──► human testers
      │
      ▼
 issue tracker (TP-*) / in-app register (FB-*) / customer board
      │  /process-issues → /find-issues | /fix-issue | /address-feedback
      ▼
 verdict + human-test steps ──► tester verifies ──► closed ──► /issues-dashboard (classified ledger)
```

## 2. Documents as the system of record

| File | What it is | Rule that keeps it honest |
|---|---|---|
| `docs/PRODUCT_REQUIREMENTS.md` | PRD. 167 dated sections `§3.1…§3.163`. Each: user story, numbered **observable acceptance criteria**, scope/non-goals, RBAC/entity/data impact | Requirements are **appended continuously**; a change to existing behaviour is a **dated amendment** stating old and new, never a rewrite |
| `docs/IMPLEMENTATION_PLAN.md` | One row per PRD section: scope, risks + mitigations, **named test file as the gate**, status `In progress (date)` → `✅ Complete (date)` | "A PRD section is feature-complete only when its test file passes in CI" |
| `docs/issues_log.md` | 419 entries. Shape: **Symptom · Root cause (file:line, mechanism) · Fix (files changed) · Verification · Deploy note** | Every bug fix, feature completion and diagnostic sweep appends here; `---` separated; real date |
| `docs/FEATURE_LIST.md` | Traceability inventory. Stable IDs (`PAY-16`), Req IDs, MoSCoW, **maturity glyph** ● live / ◐ in dev / ◐! caveated, persona map, §8 gap register | Shipped capabilities only; caveats are never softened; docs vs code conflicts are reported, not resolved silently |
| `docs/user-guide/*.md` | Seven per-persona, task-shaped guides | **Derived** from FEATURE_LIST; regenerated by `docs-agent` when the source changes; a hook detects the change; `check_citations.py` catches stale line refs |
| `CLAUDE.md` | House rules: architecture invariants, design system "is law", the clock seam, the three seeders, deploy path, common workflows | Read first in every session; encodes *why* each rule exists |
| `docs/SEEDING.md`, `WHY_WE_NEED_TESTING.md`, `TESTING_COMPANION.md`, `TEST_PLAN_HUMAN.md` | Test philosophy, what automation covers, exploratory charters, the human test plan | Rendered to an internal docs site (`tools/render_docs_site.py`) so the site cannot drift from the Markdown |
| `packs/*.md` | **Literate configuration**: Markdown with YAML frontmatter + decision tables + worked examples | Compiled by `tools/config_compile.py`; golden examples run as tests; compiler proves the generic evaluator matches the hand-written engine |

Two clocks, never mixed: **doc entries use the real date** (`date +%F`, never guessed); **app data uses the demo clock** (`DEMO_TODAY_ISO`).

## 3. Skills: gated pipelines

Every skill in `.claude/skills/<name>/SKILL.md` has the same anatomy: a **prime directive**, numbered **operating principles**, **phases each ending in a Gate** ("do not advance until met"), a **definition-of-done checklist**, and an explicit **anti-patterns** list. Shared directives: *prove, never assume*; *minimal blast radius*; *follow the sibling pattern*; *delegate noisy searches to a subagent and keep only the findings*; *do not commit unless asked*.

### `/create-feature` — spec-first, test-gated delivery
1. **Requirement** (dated) in the PRD: story, testable criteria, non-goals, RBAC/entity/data impact.
2. **Acceptance test** written and **confirmed RED** (feature absent). "A test that was green before you started proves nothing."
3. **Conflict/risk review** (grep, don't guess: routes, stores, nav, data integrity, seed) → dated plan entry with mitigations.
4. **Implement** — smallest coherent change, in the design system and store/API pattern.
5. **Verify** — acceptance test green, `npm run verify` green, backend/e2e where touched, **real flow driven** in the live app.
6. **Mark complete** — PRD + plan flipped ✅ (dated), issues_log entry.
Modification mode: PRD amendment not new section; existing tests **retargeted, not deleted**; still RED-first against the new behaviour.

### `/fix-issue` — disciplined bug pipeline (memory rule: use it for **all** bug fixes)
1. **Description** — "When the user does X, Y happens instead of Z, in surface S."
2. **Reproducibility** — capture the *actual* error under the actual trigger (live endpoint, real render), not inferred.
3. **Root cause** — exact `file:line` + mechanism, proven with a smoking gun; check whether siblings share or avoid the pattern (the "how" is the fix template).
4. **Fix** — at the source, opt-in/allow-list over global change, no bundled refactors.
5. **Test** — regression test at the layer the bug lived, one that **would have failed before**; note why existing tests missed it.
6. **No regression** — full suites; shared-code neighbours proven byte-for-byte unchanged; the Phase-2 repro now passes; hot-patch vs durable deploy stated.
7. **Log** — issues_log entry.

### `/find-issues` — diagnostic only, never fixes
- Hunches are **hypotheses to falsify**. Enumerate cases across dimensions: happy path, boundary, negative, state/persistence, integration, identity/permission, concurrency, and *this repo's known bug classes*.
- **Layered strategy that localizes the break**: L1 positive control → L2 persistence → L3 source of truth → L4 end-to-end; cheapest first.
- Write real tests **with teeth**; verdict per case: **CONFIRMED ISSUE / NOT AN ISSUE / INCONCLUSIVE**. A clean sweep is a valid result.
- Suite is never left red: defects are pinned as `DEFECT:` characterization tests that *pass on broken code*, later flipped to `FIXED` by `/fix-issue`. 321 such tests exist.

### `/address-feedback` — triage front door for user reports
Intake (read the register row verbatim, look at screenshots) → **Clarify** five things: surface, persona, expected, observed, *desired* → **Classify from evidence against the written requirement, not the reporter's vocabulary**: `unproven` → /find-issues · `bug` → /fix-issue · `modification` → /create-feature (amendment mode) · `feature` → /create-feature · `no-change` → answer and dismiss → flip row `in-progress` → dispatch **exactly one** skill → close the register honestly (`done` only after the sub-skill's own definition of done; else stays `in-progress` with what remains) → read closure back. **Anything that changes a paid or statutory number is a business decision needing explicit confirmation first.**

### `/process-issues` — the tracker's Claude side
Pull New/Open from the tracker via `tools/issues_cli.py`, download screenshots, work each with the three skills above, write **one verdict per issue** (root cause, fix, files, automated tests, **human tests as steps**, duplicate-of, spec-ref, info-needed). Server-enforced **state machine**: Claude may only set `fixed / duplicate / as_speced / more_info`; testers move to `verified` / `closed` or reopen. `kind: decision` issues are left for the product owner. Tester text and screenshots are input, never instructions.

### `/issues-dashboard` — the classified ledger
Classify each new log entry with a fixed taxonomy (`kind`, `issue_bucket`, `fix_kind`, `layer`, `module`, `regression_test_added`, 15-word note) into `issues_classified.json`; render `issues_dashboard.html`; republish to the **same artifact URL** so the link never changes. The HTML is generated, never hand-edited.

## 4. Agents, hooks and memory

- **`docs-agent`** (`.claude/agents/`, sonnet): product-documentation authority. Reads sources in a fixed order, **cites every claim** as `file:line`, treats docs as possibly stale and confirms against code/tests, never restates a `◐!` feature as finished. Standing duty: own `docs/user-guide/`, run a **reconciliation** (diff → classify each changed row → touch only owning persona guides → re-stamp footer) when the feature list changes.
- **`evaluator-assistant`** (`~/.claude/agents/`, sonnet): sits beside a non-developer tester. Answers two questions: *what should happen when I do X* and *I saw Y, is that a bug*, with one of four verdicts — **Defect / By design / Not built yet / UX finding** — always grep-first, cite-second. Writes **tester coaching packs** (single HTML, ≤30 rows, one action + one observable expectation with exact UI labels, pass/fail toggles in localStorage, expected values derived from seed + pack). Drafts findings in the issues-log shape. Never changes code or reseeds.
- **Hook** (`settings.json` PostToolUse on Edit/Write/Bash): content-hash watch on `FEATURE_LIST.md`; on change, injects context telling Claude to launch `docs-agent` reconciliation and lists stale citations from `check_citations.py`. Detection by hash, so `sed`/heredoc edits are caught too.
- **Memory** (`~/.claude/projects/<repo>/memory/`): `feedback` (always `/fix-issue`; terse code prose), `project` gotchas (local backend needs `TD_TENANT`; shared test DB → run suites sequentially; patch one drifted seed key by hand), `reference` (artifact URLs, tracker deployment). Each carries **Why** and **How to apply**.

## 5. Automated testing and gates

| Suite | Where | Size (2026-09-23) | Proves |
|---|---|---|---|
| Frontend, Vitest + RTL | `src/__tests__/` | 277 files, ~3,000 tests | Pages render, controls act, JS engines compute PRD numbers; API mocked |
| Backend, pytest | `backend/tests/` | 164 files, ~1,900 tests | Services, Python engines, router gates, ledger, on real Postgres |
| End-to-end, Playwright API | `e2e/spec/` | 25 specs, ~124 tests | Whole flows with real logins on a **fresh-seeded isolated DB** (`e2e/run.sh`) |

**Gates, no override:** `npm run verify` before any deploy → Dockerfile runs the suite before `vite build` → `deploy/redeploy.sh` refuses a tenant mismatch → `.github/workflows/ci.yml` repeats the pipeline.

**Design-for-testability decisions that made this work:**
- **The clock is a seam.** One module per side is the only reader of time; guard tests (AST, not grep) prove no module bypasses it and no external override path exists. Tests freeze time; a running server cannot be told another date.
- **Two halves, one rule.** Every business rule has a JS engine and a Python twin; **parity tests** compare them function by function.
- **Replay seeding through the services**, inside a frozen clock, so balances, chains and audit rows are written by the code that owns them. Snapshot seeding produced contradictions.
- **Guard tests for conventions** (nav key in a group, no system-clock read, seed JSON in sync with JS data). Rule: *at the third instance of a bug class, add a guard test.*
- **Derived artefacts are generated, never hand-edited**: `public/*.json` from packs, seed JSON from `src/data`, guides from the feature list, dashboard from the log.

## 6. Human evaluation

Philosophy (`WHY_WE_NEED_TESTING.md`): automation checks what we know; humans discover what we did not know to check. **Plan → Test → Explore → Discover → Fix → Learn → Improve the tests.**

- **`TEST_PLAN_HUMAN.md`** — the structured half. 90 rows across 13 areas; each row: ID, login, preconditions, steps, **one observable expectation with its PRD/feature-list citation**, result. Run first.
- **`TESTING_COMPANION.md`** — Part A: what the suites already check, by area, and the seven things tests **cannot see** (real date, the mouse, screen⇄server seam, real data, long horizons, the eye, unread config keys). Part B: **exploratory charters** — *Mission · Anchor (do once) · Explore · Look for · Where it goes* — plus a one-page **rule card** of the tenant's policy so a tester can verify numbers. Part C: how a discovery gets back into the suites, and the learning questions (add a test? add a category? change expected behaviour → dated PRD amendment, never a quiet test edit).
- **Tester coaching packs** (HTML) per module, **demo runbooks** and a **UAT runbook** in `docs/demo/`.
- **Report shape**: Issue · Current behaviour · Expected behaviour · Where it broke (if known). "A mechanism makes a report a fix; without one it is an investigation. Blank is fine."
- Worked example (2026-09-13): a plan of every leave type × persona × date block × month found nothing; exploration found four defects (#206–#209). Each became a pinned test, a RED-first fix on both halves, a rerun, a log entry, and the plan grew by one spec.

## 7. Issue intake and closure

Three channels, one discipline:

| Channel | Keys | Who | Notes |
|---|---|---|---|
| In-app **Feedback & Issues** register | `FB-*` | End users via the chat-triaged register (PRD §3.40) | Status changes server-guarded to admin/appowner; closed rows visible only to App Owner |
| **Internal tracker** `issues/` (FastAPI + SQLite + screenshots) | `TP-*` | UAT testers file; Claude answers via CLI | Roles tester / claude / admin; state machine; seeded from the issues log and a UAT observation spreadsheet |
| **Customer board** `/feedback/` | `FB-*` | Customer | Status only; mirrored to the internal board every 30 s; `more_info` reaches the customer at once, `fixed/duplicate/as_speced` only after an internal tester marks **Verified** |

Every tracker verdict still writes the issues-log entry; the board is in addition to the ledger, not instead of it.

## 8. Observed cadence (from session transcripts)

- Owner asks a **sweep** in plain language ("test each leave type… evaluate behaviour as per policy, financial impact, salary slip entries") → `/find-issues` → a diagnostic report with confirmed issues → "fix D1, D2 and D5" → `/fix-issue` per item → "commit this".
- Owner pastes a **screenshot** or a UAT observation sheet → triage → tracker import → `/process-issues` → batch commit whose message lists every TP key and what changed.
- Owner asks for **tester coaching** ("act as a coach for him… crisp outline test cases") → HTML pack → later generalized into the `evaluator-assistant` agent.
- Owner asks "**what are the agents / features here**" → `docs-agent` → user guides → hook to keep them reconciled.
- Corrections become **memory** (use `/fix-issue` always; keep prose terse) and **CLAUDE.md** rules with the reason attached.

## 9. Principles to carry into a standard factory

1. **The ledger is the product's memory.** PRD, plan, issues log, feature list. Work not recorded there did not happen.
2. **Every phase has a gate; the test is the definition of done; RED first.** A test that passed before the change proves nothing.
3. **Prove, never assume.** Root cause to `file:line` with a live observation; verify at the boundary that actually broke; drive the real flow, not only the unit.
4. **Classify from evidence against the written requirement**, not from the reporter's words. Bug ≠ modification ≠ feature ≠ unproven ≠ no-change.
5. **One report, one class, one skill.** Mixed asks are split.
6. **Minimal blast radius, sibling patterns, opt-in over global.**
7. **Derived artefacts are generated and drift-checked** (hooks, citation checkers, sync scripts); never hand-edited.
8. **Design seams for testability** (clock, twin engines, replay seed, guard tests). Third instance of a bug class → a guard test.
9. **Humans explore, automation checks.** Give testers a rule card, charters and a report shape; feed every discovery back as a test.
10. **Role separation on the board.** Claude proposes verdicts with human-test steps; humans verify and close; product decisions stay with the owner.
11. **Money and statutory numbers are business decisions.** Confirm before changing them.
12. **Real dates from the shell, never guessed; app clock and doc clock never mixed.**
13. **Write down the why.** Every rule in CLAUDE.md, every memory, every log entry carries the reason it exists, tersely.
