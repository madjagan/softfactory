A spec-first framework for Claude Code

Software, built to spec.

softfactory turns a product summary into a repo that runs as one gated loop. Requirements are dated, every change starts with a failing test, nothing ships until the gates are green, and a ledger records every decision. Agents work the queues. People make the calls.

One loop for the whole lifecycle

From the first interview to the thousandth fix.

Each stage is a skill with the same shape: a prime directive, phases that end in gates, a definition of done and a list of anti-patterns. The stages hand off through the ledger, so nothing depends on anyone remembering.

Know who it is for before you write a line

A command-line interview with the product owner. It pushes back on vague answers, plays every section back for confirmation and resumes where it stopped.

/product-interview

Personas, a value proposition canvas per primary persona (jobs, pains, gains and the fit), component tools, alternatives, 3-month success metrics, stack and deploy.

writes docs/PRODUCT_SUMMARY.md → read by /setup-project

A repo that knows how to run itself

The summary becomes the manifest and the ledger. The verify and deploy gates are proven before the first feature, and the issue tracker starts. Re-run it any time to fill gaps.

/setup-project

Writes factory.yaml, the PRD skeleton with its first dated sections, the implementation plan with test gates, the issues log, the feature list, the human test plan, the testing companion and CLAUDE.md house rules.

PRODUCT_SUMMARY.md → factory.yaml · PRD · plan · issues log · feature list · test plan · tracker · gates proven

Every change starts red and ends green

Features, fixes and investigations each have their own pipeline. A test that passed before the change proves nothing, so the acceptance test must fail first.

/create-feature

Dated requirement, failing acceptance test, risk review, build, then green tests, the full gate and the real flow. Changes to existing behaviour become dated amendments.

/fix-issue

Describe, reproduce, root cause to file:line, minimal fix, a regression test that would have failed before, no regressions, then the log entry.

/find-issues

Hunches become hypotheses to falsify. Layered tests with teeth give a verdict per case. It finds and proves defects and never fixes them.

Ships only when every gate is green

The release skill confirms the tree is what you think it is, runs the full gate, deploys, smoke-tests the live instance and writes down exactly what shipped. Any red gate stops it.

/release

Smoke checks for health, asset type, version stamp and login. The release log lists the issues-log entries and PRD sections since the last release, and the tracker keys testers can now verify.

tree identified → every gate green → deploy → smoke → RELEASE_LOG.md

Listen to testers and customers, and keep the docs true

Reports, tickets and ideas each have an agent that works the queue in its own context. Test material and user guides are regenerated from the feature list, never edited by hand.

/address-feedback

Clarify, classify from evidence against the written requirement, dispatch exactly one skill, close the register honestly.

/process-issues

Launches the Issue Agent on the tracker queue. Verdicts come back with human test steps.

/process-tickets

Launches the Support Agent. It drafts replies from the docs; a person sends them.

/process-ideas

Launches the Ideas Agent. Requests from every source become one idea with its demand.

/test-pack

Human test plan, exploratory charters and a coaching pack per module.

/test-guide

A one-page tester's guide with control labels checked against the source.

/guide-screenshots

An annotated screenshot storyboard for a guide, and narrated videos on request.

/issues-dashboard

Classifies the issues log into the Issue Ledger page, at a link that never changes.

The ledger

One requirement, traced end to end.

Every line of the ledger says where it came from. A requirement points to its test, the test to its log entry, the feature to its guide. When two documents disagree, the source wins and the derived one is regenerated.

  • Requirements change by dated amendment, never a silent rewrite.
  • A section is complete only when its named test file passes in the gate.
  • User guides are derived from the feature list. A hook notices the change and the docs agent reconciles them.
  • Real dates come from the shell, never a guess.

Agents

Agents do the work. People make the decisions.

Each agent runs in its own context, so screenshots, reproductions and searches never crowd the main session. The server enforces what each one may do.

Issue Agent

Works the tracker queue. Finds the root cause to file:line, writes the fix and its regression test, and returns a verdict with steps for a human to try. It never verifies or closes.

Support Agent

Drafts replies from the user guides, the feature list and the PRD, after checking the customer's release and known issues. A person sends every reply.

Ideas Agent

Links requests from the portal, tickets and issues into one idea, drafts its public version and moves accepted ideas along as the plan and release log change. The owner accepts or declines.

docs-agent

Owns the per-persona user guides. Cites every claim, and reconciles the guides whenever the feature list changes.

evaluator-assistant

Sits beside a human tester. Says what a screen should do, and whether what they saw is a defect, by design, not built yet or a UX finding.

Agents propose. People decide.Money, statutory and access changes are business decisions and are always confirmed first.

FAQ

Questions before you install.

What do I need to run it?

Claude Code, git and Python 3. The tracker, customer boards, support desk and ideas portal are small FastAPI apps with a SQLite file each, installed alongside the skills.

Does it work with my stack?

Yes. The skills read your commands from factory.yaml: the unit, backend and end-to-end suites, the verify gate and the deploy command. A layer you leave empty is skipped.

Can I add it to a repo I already have?

Yes. Run install.sh on the repo, then /setup-project with a summary of what the product already does. Running install.sh with --update later refreshes the framework without touching your docs.

What will Claude do without asking?

It writes tests, fixes and drafts through the gated skills. It never verifies or closes an issue, never sends anything to a customer, never commits unless asked, and confirms money, statutory and access changes first.

How are customers kept apart?

Each early customer has their own board and database. The support desk and ideas portal filter every request by organisation on the server. Notes sent to customers never name another customer or an internal key.

Why must the first test fail?

A test that already passes before the change proves nothing about the change. Starting red shows the test can see the feature is missing; ending green shows it is there.

Where did the method come from?

It was extracted from a production HR system built this way over eleven weeks. The methodology and the evidence behind it are in METHODOLOGY_BRIEF.md.
